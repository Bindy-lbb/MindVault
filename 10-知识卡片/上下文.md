# 上下文

[卡片目录](README.md) · [课程入口](../20-课程笔记/第一阶段-线上课程与阅读顺序.md)

## 一句话解释

**上下文是模型这次回答实际可参考的信息；上下文窗口是输入与生成内容受到的容量约束。**像做题桌面：书柜里有书，不代表书已经摊在这次桌上。

## 为什么需要它

MindVault 笔记已经保存，并不代表某个模型请求看到了它。要检查应用是否读取了相关内容，是否真的放进请求，才能解释“为什么模型不知道我写过的事”。

容量通常用 Token 表示，不同模型与模式的计算规则不同。初学先关注材料是否相关、要求是否清楚，以及是否为回答留出空间。

## 用 MindVault 走一遍

假设笔记写着：“本周只练 Python 文件读取，暂时不做模型部署。”问“今天学什么”时，把这句话一起提供，就能作为个人安排依据；只给问题而没有计划，模型不应凭空知道你的约束。

项目 02 的文章整理会读取指定正文，放进 user 消息；system 消息提供整理规则。`--source-url` 只用于草稿记录来源，当前不会抓取网页，也不会自动把链接后的正文送入模型。

| 内容 | 是否自动可用 |
| --- | --- |
| 硬盘上的整座 MindVault | 不自动进入请求 |
| 当前 messages 中的正文 | 会随请求提供 |
| 上一次回答 | 只有本次带入历史或服务有对应机制才可用 |
| 模型参数中的能力 | 与这次提供的资料不同 |
| 应用保存的记忆 | 要由应用选择、取回并提供 |

假设窗口预算 10000 Token，规则和资料 7000、历史 2000，还计划生成 2000，则合计 11000，已经超出这个简化预算。真实规则依服务，但“全部容量都给文章”往往不合适。此数字是演算，不对应本库当前模型上限。

## 每一步的输入输出

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 选材料 | 当前问题与相关笔记 | 必要段落 |
| 组织 | 规则、任务、资料、必要历史 | messages |
| 检查长度 | 完整输入及输出预算 | 可请求或需缩减 |
| 调用 | 实际上下文 | 生成回答 |
| 核对 | 回答与已提供材料 | 是否遵守约束、依据是否充分 |

后续 RAG 就把“从书柜找相关页再放到桌上”组织成程序。

## 常见疑问

**聊天界面所有历史都一定发给模型吗？**应用可能摘要、截断或检索，界面可见不等于请求完整包含。

**上下文更大就一定理解更好？**相关性、结构和模型能力仍影响结果，长度不代替质量。

**提供资料等于永久记住吗？**当前输入与长期保存不同；系统要另有保存、选择和再次提供逻辑。

**只给链接是否足够？**要确认应用确实能读取正文。当前第二阶段脚本不会自行抓网页。

**截断任意一半可以吗？**可能丢掉关键条件。先选择与问题有关的材料，再按用途拆分或总结，并保留来源。

## 小练习与自测

**题目：**笔记在私有 GitHub，模型回答就一定引用得到吗？

**参考答案：**还要看应用权限、读取过程和本次请求内容。文件存在只是第一步。

**练习：**对同一任务分别提供和不提供个人计划，记录实际输入差异；真实模型输出需自行运行后再填。

### 动手记录

- [ ] 给模型一段自拟计划再问学习安排，检查回答是否使用了计划。
- [ ] 另开一次不包含该计划的请求，比较结果；在笔记中记录实际提供了哪些材料。
- [ ] 用自己的话解释：“我的笔记在电脑里，模型为什么还需要读取它？”
- [ ] 资料过多时，如何挑选最相关的段落？留到 RAG 阶段实践。
