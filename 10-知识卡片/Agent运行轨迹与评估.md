# Agent 运行轨迹与评估

[卡片目录](README.md) · [第四阶段课程](../20-课程笔记/第四阶段-工具调用与Agent课程及实践顺序.md)

## 一句话解释

**运行轨迹记录发生了什么；评估判断做得是否符合任务。**像实验记录既要写操作步骤，也要检查实验结论。最终一句“完成了”不能代替过程证据。

## 为什么需要它

相同的答案可能来自真实读取，也可能来自猜测。只有最终内容，看不出有没有走错工具、反复重试、超出预算或漏掉任务要求。

评估也不能只看程序退出码。当前脚本允许依据不足正常结束，这种诚实退出是合理行为，但没有完成“生成复习题”的原始目标。必须同时记录任务结果和执行结果。

## 用 MindVault 走一遍

运行成功演示后会生成三个文件：

| 文件 | 适合看什么 | 不代表什么 |
| --- | --- | --- |
| result.md | 题目、依据和人工核对项 | 内容已经全部正确 |
| trace.json | 模式、停止原因、次数、事件、资料版本 | 模型的隐藏思考全文 |
| messages.json | 发给模型的消息和调用回执 | 下次会自动恢复的记忆 |

先看 execution_mode：scripted 是预写响应，live 才有真实模型请求。成功 scripted 应有 3 次响应、2 次工具尝试、completed；bad_arguments 是 4 次响应、3 次尝试，第一次工具错误不能从记录中抹去。

再从题目回到依据：问题是“密钥建议放哪里”，答案为“环境变量”，对应原文确实如此。如果答案改成“提交到 Git”，引文却仍是“建议放在本地环境变量中”，逐字匹配可能通过，语义检查应判失败。

最后检查要求：用户要一题，是否实际给了一题？脚本只检查 1–5 条的通用结构，不会自动核对所有自然语言要求。任务完成度需要另判。

## 每一步的输入输出

| 层次 | 输入证据 | 应记录的结论 |
| --- | --- | --- |
| 任务完成 | 用户要求与最终题目 | 数量、主题、答案是否符合 |
| 工具行为 | tool_result 事件 | 工具与参数是否合适，有无无效重复 |
| 引用依据 | read_note 原文 | 引文存在且支持答案吗 |
| 受控结束 | stop_reason 与计数 | 完成、缺依据、预算或错误 |
| 请求成本 | 模式、usage、耗时 | 真请求多少，哪些信息未测 |

trace 记录的事件耗时不等于完整端到端耗时；若要比较总体延迟，需要另计整个运行时间。

## 常见疑问

**如何比较两个版本？**使用同一组任务、相同资料与预算，一次只改一个因素，例如工具描述。保留成功和失败。模型可能有波动，真实效果不能只靠一次好结果判断。

**成功率怎么算？**先定验收标准。假设手工评估五个有答案任务，其中四个符合全部要求，则该小样本任务成功率是 4/5=80%。这是演算示例，不是本库实测指标；无答案任务应另看是否合理拒答。

**usage=null 表示零费用吗？**scripted 没有外部请求，当然没有模型调用费；live 如果缺 usage，只能说明用量未记录，不能推出零费用。

**需要保存隐藏推理吗？**不需要。记录可观察的请求、工具、结果与错误足以定位许多问题，不能用日志推断完整内部思考。

## 小练习与自测

**题目：**引文存在、答案却和引文矛盾，如何记录？

**参考答案：**格式与引文存在检查通过，语义依据检查失败。不要只写“测试通过”。

**练习：**对 success 和 bad_arguments 各填一行评估表。两者最终都可能完成，但后者多一次请求和工具尝试，恢复成本不同。

### 动手记录

- [ ] 找到一次失败发生在工具前、工具内还是最终内容检查。
- [ ] 人工判断一条复习题的答案与引文是否一致。
