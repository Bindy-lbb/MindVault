# KV缓存与内存预算

[卡片目录](README.md) · [进阶课程](../20-课程笔记/进阶阶段-模型原理本地部署与微调.md)

## 一句话解释

**KV Cache 保存已处理位置在各层的注意力键和值，让生成下一 Token 时复用历史计算。**它像临时计算草稿，减少重复工作，同时需要额外空间。

## 为什么需要它

自回归生成不断沿用前缀。如果每一步都重算全部历史，长回答的开销会更大。缓存能复用过去的 K/V，但长度、批次和并行请求增长时，也可能成为内存压力来源。

所以“模型权重装得下”和“长上下文稳定运行”需要分别检查。模型允许的最大长度，不等于自己的设备能以该长度服务所有请求。

## 用 MindVault 走一遍

提问“解释 Token”时，先处理整段提示，常称 prefill；随后逐 Token 生成，常称 decode。decode 时新位置的 Q 会结合已缓存的历史 K/V，不是完全不看历史，也不是只保存上一个词。

用一个全层、全长度缓存的简化预算：

`KV 字节数 ≈ 2 × L × B × T × Hkv × D × S`

| 符号 | 含义 | 教学值 |
| --- | --- | --- |
| 2 | K 与 V 两份 | 2 |
| L | 层数 | 24 |
| B | 同时处理的序列数量 | 1 |
| T | 缓存的位置数 | 2048 |
| Hkv | KV 头数 | 8 |
| D | 每个头的维度 | 64 |
| S | 每个缓存元素字节数 | 2 |

相乘为 100663296 字节，即 96 MiB。其他不变，T 翻倍约为 192 MiB。这是虚构架构演算，不是 Qwen 或本机实测；实际还受分组查询注意力、滑动窗口、缓存策略、分页与额外分配影响。

Hkv 不一定等于查询头数。模型若共享部分 K/V 头，不能简单套用总注意力头数。权重做 4-bit 量化也不表示 KV 同样是 4-bit，两种设置要分别确认。

## 每一步的输入输出

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 处理提示 | 模板化输入、模型权重 | 初始缓存和下一步得分 |
| 生成一个 Token | 新位置与历史缓存 | 新输出、扩展缓存 |
| 规划容量 | 架构、长度、并发、精度 | 粗略缓存预算 |
| 小规模实测 | 短问题与有限输出 | 实际峰值和耗时 |
| 逐项扩大 | 更长输入或并发 | 资源变化与可用范围 |

不同后端可能预分配容量，也可能动态增长；本例比例是估算，不承诺任务管理器显示严格线性。

## 常见疑问

**KV Cache 是知识库或永久记忆吗？**不是，它是推理计算状态。清理后不应期待模型记住你的笔记，也不改变权重。

**上下文窗口只计算输入吗？**通常还要为生成内容和模板预留空间。具体限制依后端检查，别把窗口全部填成问题。

**为什么第一次慢、后面快？**可能涉及模型加载、预填充和系统缓存；不要把这些全归因于 KV。分别记录加载和生成耗时。

**训练也一直开推理缓存吗？**用途不同。本库真实 LoRA 训练设置 use_cache=False，不把生成时缓存优化原样当训练策略。

**本库客户端怎么限制？**请求中 num_ctx=1024、num_predict=128，只是教学起点，不是对所有设备的资源保证。

## 小练习与自测

**题目：**其他条件不变，把序列数从 1 增到 4，理想 KV 预算怎样变化？

**参考答案：**约四倍。真实服务可能有共享或不同分配策略，仍需实测。

**练习：**先写预算公式，之后若做 live，再逐步加长输入、记录内存和延迟。未运行就保留待测，不用估算冒充实测。
