# 文档加载与元数据

[第三阶段阅读顺序](../20-课程笔记/第三阶段-RAG课程与实践顺序.md) · [项目 03](../30-项目实践/03-RAG知识库问答/README.md)

## 一句话解释

**加载是把文件里的内容读出来；元数据是描述内容来源和属性的信息。**正文像复印的书页，元数据像旁边写下的书名、页码和版本，帮助你回头核对。

## 为什么需要它

模型不能仅凭电脑里存在一个文件，就知道文件内容。程序首先要找到文件、读出字节，再按正确编码解释为文字。

只留下文字也不够。两篇文章可能都说“密钥放到环境变量”，但一篇是旧草稿，一篇是新版本。缺少文件位置与版本信息时，搜索结果无法说明它引用的是哪份资料。

“元数据”不要求复杂系统：文件路径、标题、行号都可以是元数据。更完整的系统还可能保存作者、时间和访问权限，但要有对应的来源和处理逻辑。

## 用 MindVault 走一遍

为回答“API 密钥应该放在哪里，能写进 Git 吗？”，先读取项目中的 `01-API配置.md`。它第 4–5 行是本例的关键依据。

下面为了说明字段，只取这两行，省略真正的片段 ID；**它不是默认切分参数生成的完整索引记录**：

```json
{
  "path": "01-API配置.md",
  "title": "API 配置示例",
  "start_line": 4,
  "end_line": 5,
  "text": "API 密钥用于认证调用方，建议放在本地环境变量中。\n不要把真实 API 密钥写进 Markdown、代码或 Git 提交。"
}
```

`path` 是相对于选定资料目录的路径；`title` 是人读的名称；起止行从 1 开始、两端都包含；`text` 是实际材料。于是读者可以根据路径打开文件，再根据行号找到原句。

同一个标题可能重复，路径能进一步定位；路径对应的内容也可能改变，因此还需要版本线索。本项目用 SHA-256 为文件内容计算一个摘要：文件字节变化，摘要通常就会变化。它能帮助发现变化，但不能判断资料是否真实、是否有权使用。

## 每一步的输入输出

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 选择资料 | 一个明确的资料目录 | 待处理的 Markdown 文件集合 |
| 读取与解码 | 文件字节 | UTF-8 文字 |
| 记录文档信息 | 路径、全文 | 路径、文件摘要等记录 |
| 切分并附来源 | 文本和文档信息 | 带标题、行号、正文与 ID 的片段 |
| 返回检索结果 | 命中的片段 | 原句及可以追溯的位置 |

“Document”通常表示整份资料的容器；“Node”或“chunk”表示从资料拆出的片段。你可以先记成“整篇笔记”和“笔记中的一段”，不用先掌握某个框架的类名。

## 常见疑问

**Obsidian 顶部的 status、tags 也是元数据吗？** 是。但写进笔记的属性不会自动变成检索过滤条件。当前脚本没有把这些 YAML 属性解析为专门的筛选字段，它们仍可能作为正文参与按行切分。

**有行号就能一直准确定位吗？** 插入一行之后，后面的行号就会移动。引用必须结合当时的文件版本；资料变化后应重建本项目的索引。

**片段 ID 永远不变吗？** 当前 ID 取决于文件路径、行区间和文件内容摘要。同一资料版本、相同切分下可重复得到；改了全文或切分后可能改变。回答中的 `S1` 则是本次请求临时分配的来源编号，不能当作全库永久 ID。

**PDF、图片、网页都能直接这样读取吗？** 当前练习只读取 UTF-8 Markdown。PDF 可能要解析页面，扫描件可能要识别图片文字，网页要提取正文；这些步骤可能改变排版或漏内容，需要额外检查。

## 本库实现与实践入口

项目保存文件清单 `manifest`，其中是相对路径与 SHA-256；片段列表 `chunks` 保存正文及来源。标题取第一个一级标题，没有时使用文件名。读取材料不会执行其中的命令，也不会自动读取网页和附件。

跟随[实践一](../30-项目实践/03-RAG知识库问答/实践一-加载切分与关键词检索.md)建索引，选一个实际片段核对路径、行号和正文。
