# 文档切分与重叠

[第三阶段阅读顺序](../20-课程笔记/第三阶段-RAG课程与实践顺序.md) · [项目 03](../30-项目实践/03-RAG知识库问答/README.md)

## 一句话解释

**切分把一篇长资料拆成适合检索的小段；重叠让相邻小段共享一些内容，减少边界处的信息丢失。**每段通常叫 chunk，也就是片段。

## 为什么需要它

一本学习笔记里可能同时讨论密钥、费用、模型选择。你只问“密钥能写进 Git 吗”，把全文发给模型会夹带大量无关内容，也更占上下文。

切分让系统可以只找相关部分。但切得太碎，条件与结论会分开；切得太大，相关句子会淹没在别的内容里。目标是让每块尽可能保持一个完整意思，同时控制长度。

重叠像地图相邻页重复的一小圈区域，帮助跨边界衔接。它增加了重复材料，并不能保证所有语义关系都被保留。

## 用 MindVault 走一遍

为方便手算，假设一份教学笔记有 20 行，每块 8 行，重叠 2 行。下一块前进的步长就是 `8 - 2 = 6` 行：

| 片段 | 起止行 | 与上一块共享什么 |
| --- | --- | --- |
| A | 1–8 | 第一块没有上一块 |
| B | 7–14 | 第 7–8 行 |
| C | 13–20 | 第 13–14 行 |

如果“只有测试环境允许使用演示密钥”在第 8 行，“生产环境必须使用独立密钥”在第 9 行，不重叠时两句可能分开；当前重叠使 B 同时包含两句。这里的文字是为演示边界手写的假设材料。

贯穿本阶段的真实问题是“API 密钥应该放在哪里，能写进 Git 吗？”项目的 API 示例第 4–5 行同时给出存储建议和禁止提交的要求。默认 8/2 切分的第一块会包含这两句；若把两句拆开且只检索到一句，答案可能不完整。

## 每一步的输入输出

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 确定规则 | 文档、每块大小、重叠大小 | 本次切分配置 |
| 移动窗口 | 按顺序排列的行 | 一组行区间 |
| 提取内容 | 行区间 | 对应原文片段 |
| 保留来源 | 片段及原文件信息 | 带路径、起止行和 ID 的记录 |
| 用问题检查 | 片段和测试问题 | 是否保留了回答所需的条件与结论 |

这里按“行”切，便于理解。实际资料的一行可能是一句短话，也可能是几千字；行数不能代替 Token 长度。Token 是模型处理文本的单位，字符数和 Token 数也没有固定的一一对应关系。

## 怎样选择切分方法

先试按标题和段落保留主题，超长段落再按长度拆分。表格中的表头与数据、代码中的完整函数、结论前的适用条件，都值得一起检查。当前脚本实现的是按行切分，这些更细的策略是后续改进方向。

初学时，用同一组问题比较两种配置即可：例如 8/2 与 4/1，观察正确证据是否出现、是否带齐条件、是否返回太多重复。没有一个对所有资料都最好的块大小。

## 常见疑问

**重叠越大越好吗？** 重复片段可能挤占前几个检索名额，也会重复消耗上下文；应结合边界遗漏来调整。

**把 K 调大能修复切断的问题吗？** 可能找回另一块，但未必。如果另一块关键词很少、排名靠后，仍可能漏掉。优先检查切分是否保留完整意思。

**8/2 是通用推荐吗？** 只是本项目的教学参数，用于展示行号与重叠，不能直接当生产配置。

## 小练习与自测

用纸写出 12 行文本，在第 4 行写条件、第 5 行写结论。按 4/0 和 4/1 各切一次，找出能同时包含两行的片段。

参考答案：4/0 得到 1–4、5–8、9–12，条件与结论分离；4/1 得到 1–4、4–7、7–10、10–12，第二块包含两行。仍要检验检索能否把第二块找出来。

## 本库实现与实践入口

脚本要求每块 1–100 行，重叠非负且小于块大小；这些是教学实现限制。片段保存原文，不自动概括。语义选修另检查 Embedding 模型输入长度，过长时会报错。

在[实践一](../30-项目实践/03-RAG知识库问答/实践一-加载切分与关键词检索.md)用不同配置建立两个新索引，再比较相同问题；记录一个分块改善或变差的例子。
