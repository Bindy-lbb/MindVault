# 结构化日志与可观测性

[卡片目录](README.md) · [第五阶段课程](../20-课程笔记/第五阶段-评估与部署课程及实践顺序.md)

## 一句话解释

**结构化日志把事件写成固定字段；可观测性帮助你从运行证据判断系统发生了什么。**像实验记录里有时间、编号、步骤和结果，方便回查，而不是只留“失败了”。

## 为什么需要它

一个用户说“搜索不出来”，可能是正常无命中、参数错误、索引过期，也可能是请求根本没到服务。没有证据，这些情形看起来都像同一个问题。

日志应提供足以定位故障的上下文，同时避免收集无关正文。第四阶段完整消息轨迹含原文，第五阶段服务元数据日志有不同用途，不能混用保存边界。

## 用 MindVault 走一遍

服务每处理一条 GET 请求，写一行 JSON，格式叫 JSON Lines。以下为虚构示例，不是实际测得的请求或耗时：

```json
{"time_utc":"2026-10-29T02:00:00+00:00","request_id":"demo-a1","route":"/search","status":200,"latency_ms":1.2,"hits_count":1}
```

| 字段 | 作用 | 查错时怎么用 |
| --- | --- | --- |
| time_utc | 对齐事件时间 | 跨时区记录时统一查看 |
| request_id | 这一条请求的编号 | 与响应中的 ID 配对 |
| route | health、ready、search 或 unknown | 知道访问哪类功能 |
| status | HTTP 状态码 | 区分成功、参数错、索引故障 |
| latency_ms | 处理耗时 | 定位明显慢请求 |
| hits_count | 命中片段数量 | 区分有候选与正常空结果 |

响应里拿到 request_id 后，在 events.jsonl 找同一 ID。200 且 hits_count=0 表示本次无候选；400 先查参数；503 先查索引和资料。元数据不会告诉你用户问题全文，所以重现语义问题时要另取得允许使用的实验输入。

这里关闭处理器自带的原始 URL 日志，服务日志不写 q、笔记正文、请求头或密钥。URL 中可能含查询内容，即使放在 localhost，浏览器历史或调用方仍可能另有记录；“服务没写正文”不是所有软件都无记录。

## 每一步的输入输出

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 接收请求 | 路由和参数 | 唯一请求 ID |
| 执行处理 | 有效索引与参数 | 状态、命中数量 |
| 回应 | 结果与 request_id | 调用方可对照的响应 |
| 写事件 | 固定元数据字段 | 一行可解析 JSON |
| 定位问题 | ID、状态、时间 | 故障层次与下一步实验 |

默认日志是逐行追加，读取时每行单独解析，不把整个文件当成一个 JSON 数组。

## 常见疑问

**日志、指标和轨迹有什么区别？**日志描述单个事件；指标汇总一段时间的数量和分布；轨迹把一个任务跨多步的调用串起来。当前有服务事件和第四阶段轨迹，没有完整监控平台。

**日志越多越好吗？**只记录定位所需内容。原样打印环境变量、整份 API 响应或所有笔记，既增体积也扩大资料传播。

**没有报警算有可观测性吗？**已有部分观察证据，但不等于完整运维能力。当前无报警、日志轮转、远程采集或长期保留策略。

**状态 200 就说明内容正确吗？**只说明该请求按接口成功处理。原文是否适合问题、答案是否正确仍需评估。

**request_id 是用户身份吗？**不是，它标识一次请求。当前没有登录身份与用户权限体系。

## 小练习与自测

**题目：**要判断一次搜索是否失败，需要把整个知识库写进日志吗？

**参考答案：**不需要。先用 ID、路由、状态和索引信息定位层次，必要时在允许范围内重现输入。

**练习：**一次正常查询、一次缺 q 查询，按响应 ID 找两行日志，核对状态差别，并检查日志没有问题正文。

### 动手记录

- [ ] 发出一次成功与一次错误请求，按 request_id 找到日志。
- [ ] 检查搜索问题有没有被写进服务日志。
