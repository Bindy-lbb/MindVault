# 工具结果与消息状态

[卡片目录](README.md) · [第四阶段课程](../20-课程笔记/第四阶段-工具调用与Agent课程及实践顺序.md)

## 一句话解释

**工具结果是行动的回执；消息状态是到目前为止交给模型的对话记录。**每张回执要对应自己的调用编号，否则模型可能把读 A 笔记的结果误认成 B。

## 为什么需要它

本地函数打印出原文，只说明终端显示了它。远端模型不知道你的终端内容，只有程序把结果加入下一次请求，模型才能据此继续。

消息还要保留因果关系：先由 assistant 提出调用，再由 tool 回传执行结果。错误结果也是信息，可以告诉模型“这个参数需要改”，不应假装成成功。

## 用 MindVault 走一遍

以 `call_s1` 搜索为例，完整 assistant 消息包含调用列表，函数 arguments 是 JSON 字符串。执行完成后，程序追加下面这种消息。为看清外层格式，这里用“无命中”作为合法结果示例，不代表默认密钥查询的实际命中：

```json
{
  "role": "tool",
  "tool_call_id": "call_s1",
  "content": "{\"ok\":true,\"data\":[]}"
}
```

`role` 表示工具回执，`tool_call_id` 必须对应先前那次请求；`content` 里装着结果 JSON 的字符串。转义写法 `\"` 是在字符串中表示引号，不是字段名的一部分。

成功读取时 data 包含 note_id、start_line、end_line、text。失败时格式为 `{"ok":false,"error":{"code":"invalid_arguments","message":"..."}}`。这是本库结果约定，别的工具不必使用相同字段。

成功演示的会话顺序是：system 规则 → user 任务 → assistant 搜索请求 → tool 搜索结果 → assistant 读取请求 → tool 原文 → assistant 最终 JSON。第三次模型请求发生前，前两次工具结果已经在消息中。

## 每一步的输入输出

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 初始化 | 规则与任务 | system、user 两条消息 |
| 保留调用 | assistant 响应 | 带 tool_calls 的消息 |
| 执行与配对 | 工具名、参数、调用 ID | 同 ID 的 tool 消息 |
| 继续请求 | 累积的 messages | 模型可看见前面结果 |
| 保存记录 | 完整消息与事件 | messages.json、trace.json |

工具尝试次数、已用 ID 和成功读取的 evidence 还由程序单独维护；不应指望模型自己可靠记账。

## 常见疑问

**只有搜索摘要能作为最终引文吗？**当前程序不允许。只有成功读取会进入 evidence；这样最终引文能对应实际读取记录。

**一个响应提出多个调用怎么办？**本库逐个执行并回传，分别保留 ID；不是并行执行。协议解析最多接受单轮四个调用，整个任务还受总工具预算限制。

**调用 ID 重复可以吗？**当前解析会拒绝同批或历史重复 ID，避免配错回执。ID 表示一次调用，不是工具名字，也不是笔记 ID。

**可以直接开启思考模式吗？**本项目只实现非思考模式消息处理。迁移到其他模式或 API 时，需要核对相应消息字段，不能仅改开关。

## 小练习与自测

**题目：**原文已经在 trace.json，下一轮请求却没带 tool 消息，模型能看到它吗？

**参考答案：**不能。磁盘记录和 API 请求是两件事。应检查 messages 是否真的加入了正确 ID 的结果。

**找错练习：**搜索调用 ID 是 call_a，回传写成 call_b。先修复配对，不应让模型猜哪条结果属于谁。
