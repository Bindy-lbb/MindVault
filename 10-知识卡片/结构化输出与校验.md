# 结构化输出与校验

[卡片目录](README.md) · [课程入口](../20-课程笔记/第二阶段-模型API课程与实践顺序.md)

## 一句话解释

**结构化输出把回答放进约定字段；校验分层检查能否解析、字段是否合格、内容是否有依据。**像信息表先查格式与漏项，再查填入内容是否真实。

## 为什么需要它

后续程序不能稳定地从一大段自由文字猜标题、观点与引用。固定结构方便自动处理，也更容易发现缺字段和错误类型。

但 JSON 合法不等于内容可信，逐字引文存在也不等于它能支持观点。把检查分层，才能说清楚哪部分自动通过、哪部分仍待人工看。

## 用 MindVault 走一遍

项目 02 的真实约定使用四个字段。下面是根据配套示例文章自拟的最小有效对象：

```json
{
  "summary":["文章建议解释、举例并复习，同时核对 AI 笔记。"],
  "key_points":[{
    "point":"学习概念时应解释并举例。",
    "evidence":"学习新概念时，先用自己的话解释，再写一个具体例子。"
  }],
  "questions":[],
  "suggestions":[]
}
```

summary 为 1–3 条非空字符串，key_points 为 1–5 个对象，每项只有 point/evidence；questions 和 suggestions 各 0–5 条。四个顶层字段必须恰好符合约定，多字段也会拒绝。这是应用格式，不是服务统一摘要标准。

| 层次 | 自动做什么 | 仍不能证明什么 |
| --- | --- | --- |
| 服务结果 | finish_reason=stop、内容非空 | 事实正确 |
| JSON | 解析字符串 | 业务字段正确 |
| 结构 | 字段、类型、条数 | 观点含义正确 |
| 引文存在 | evidence 是正文子串 | 原句支持 point |
| 人工语义 | 回原文核对结论 | 未查内容全对 |

若 point 改成“文章要求每天学两小时”，evidence 仍保留真实原句，子串检查可能通过，语义评审却应失败。这是故意构造的错误例子，不作为正式知识保存。

当前 API JSON 模式还需要 response_format 和提示中明确 JSON 及样例；程序仍处理空内容、截断和格式偏差。

## 每一步的输入输出

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 定约定 | 应用需要哪些字段 | 明确形状与类型 |
| 提出要求 | 格式设置、规则与正文 | 模型生成内容 |
| 解包 | 外层服务 JSON | content 字符串 |
| 解析校验 | content、字段规则、原文 | 合格对象或错误 |
| 渲染复核 | 对象与来源记录 | 待核对 Markdown |

失败时当前脚本不自动再请求，也不生成一份被标为成功的新笔记。

## 常见疑问

**JSON 模式等于严格业务 Schema 吗？**此处只要求 JSON 对象，应用结构仍由本地校验。

**引文略改几个词可以吗？**当前要求逐字匹配，改写不通过。要换标准需明确调整程序与评估，而非悄悄绕过。

**自动校验能判断作者和日期吗？**当前不验证文章元数据，只让用户提供来源、要求模型不补造。缺信息应留待核实。

**suggestions 也当原文观点吗？**不是，额外建议单列，帮助避免混淆。

**null 分数与 0 分一样吗？**待评或无记录不是已经判错，后续评估仍保持区分。

## 小练习与自测

**题目：**所有字段正确，但观点与引文相反，是否可正式入库？

**参考答案：**不可以，应标记语义失败并修正。格式通过只是部分证据。

**练习：**在实验副本中把 summary 改成字符串，或伪造 evidence，观察两种校验失败；再构造真实引文配错误观点，人工说明问题。
