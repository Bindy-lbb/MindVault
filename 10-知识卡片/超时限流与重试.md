# 超时、限流与重试

[卡片目录](README.md) · [课程入口](../20-课程笔记/第二阶段-模型API课程与实践顺序.md)

## 一句话解释

**超时是客户端等待某项网络操作超出设置，限流是请求触及服务限制，重试是再次发送请求。**像办事窗口没等到回执、排队人数过多和重新提交材料，原因与处理办法不同。

## 为什么需要它

调用失败不应一律“再来一次”。格式错要改格式，认证错要查配置，服务繁忙才可能适合稍后有限重试。盲目重复还可能增加处理和费用。

客户端没收到结果，不证明服务端完全没有执行。先辨认错误层次，再决定是否重发。

## 用 MindVault 走一遍

本库按 DeepSeek 状态提供提示：

| 信号 | 先检查 | 重发前做什么 |
| --- | --- | --- |
| 400/422 | 请求 JSON、模型和参数 | 修正输入 |
| 401 | 凭据和认证 | 核对本地配置与账户 |
| 402 | 余额和使用计划 | 核实账户状态 |
| 429 | 频率、并发等限制 | 降低负载、查看当前规则 |
| 500/503 | 服务端错误或繁忙 | 记录、稍后确认 |
| 超时/连接失败 | 网络、服务与等待设置 | 确认状态与用量再决定 |

这些是当前服务示例，不是所有 API 统一采用的映射。限流具体维度按官方规则，不能只看到 429 就断言是“每分钟 Token 用完”。

脚本默认 timeout=60 秒，可设 1–120。它是网络等待参数，不是整个文章读取、生成、解析和保存流程的严格总计时上限。

当前没有自动重试。后续需要时可以设计：只重试可恢复错误、限定尝试次数、设置总预算、逐步增加等待并加入随机抖动。比如虚构退避间隔 1、2、4 秒，是策略演示，不是本项目已经实现。

含写入动作时还要考虑重复执行：超时可能只是回执丢了，直接重发可能创建两份内容。当前模型生成也可能产生重复计费，所以错误发生后先检查再重发。

## 每一步的输入输出

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 发请求 | 已校验参数与凭据 | 响应或网络错误 |
| 分类 | 状态码与异常类型 | 本地、认证、限制或服务问题 |
| 定位 | 模式、规模和时间记录 | 原因假设 |
| 决定 | 可恢复性与预算 | 修正、等待、停止或有限重试 |
| 验证 | 新结果及用量 | 成功或继续记录失败 |

“无依据可答”是内容结果，不是网络故障，不能靠同样请求无限重试来补资料。

## 常见疑问

**401 连发十次能修好吗？**相同错误认证通常不会自行变有效，应查凭据。

**429 就是永久封禁吗？**不一定，按具体限制与错误说明处理。

**把 timeout 调很大最好吗？**可能只是等更久，先判断网络与任务，不把等待参数当性能优化。

**SDK 自带重试会影响什么？**实际尝试数、延迟和用量可能与外层调用数不同，换 SDK 后核对默认行为。

**程序提示失败还能写已完成吗？**记录真实状态和原因，失败也是学习结果，不假装完成任务。

## 小练习与自测

**题目：**超时是否证明服务端没有计费？

**参考答案：**不能，仅说明客户端等待失败；实际处理与账单需要另核实。

**练习：**离线区分 401、429 和网络超时提示，各写一个下一步，不为练习故意向真实接口连续发错请求。
