# 版本发布与回滚

[卡片目录](README.md) · [第五阶段课程](../20-课程笔记/第五阶段-评估与部署课程及实践顺序.md)

## 一句话解释

**发布把明确版本的文件整理成可运行成果；回滚是在新版本有问题时，重新使用已验证的旧版本。**像保留好用的复习计划，新方案不合适时有明确退路。

## 为什么需要它

仓库里有代码，不等于知道哪一组代码、资料和配置已经一起验证过。直接覆盖旧文件后，可能连上一个正常状态也找不到。

所以每版使用新目录，记录文件清单和验证结果，并亲自重启旧版。只有“保留旧文件”还不够，真正恢复后要检查就绪和实际查询。

## 用 MindVault 走一遍

release.py 默认创建本地 0.1.0 发布目录，带九个列入摘要的文件：两个脚本、配置、启动说明、五篇示例笔记。另有 RELEASE.json 清单，清单不包含它自己的摘要。

| 文件或内容 | 为什么带或不带 |
| --- | --- |
| local_service.py、rag_practice.py | 独立运行检索服务 |
| notes、service.json、START.md | 明确资料、配置与步骤 |
| RELEASE.json | 版本、构建环境和文件 SHA-256 |
| 旧索引、日志、虚拟环境 | 不复制，避免旧路径和运行残留 |
| Git 历史、API Key | 不属于这个教学发布包 |

版本号如 0.1.0 是人的标记；同一号码也可能被错误用于不同目录，实际内容要看清单和摘要。脚本只检查三段数字格式，不自动决定版本升级规则。

演练过程：保存 0.1.0 → 新建 0.2.0 → 在 0.2.0 实验笔记末尾加一行 → verify 应报摘要不符 → 停止新版本 → 重新启动旧 0.1.0 → 请求 ready 和同一条密钥查询。

先把包放到最终位置再建索引，因为索引含绝对资料路径。运行数据放包内 .local；verify 允许这个目录变化，但不接受清单外其他文件。修改 service.json 也会改变摘要，不能把校验失败直接忽略。

## 每一步的输入输出

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 准备版本 | 已评估代码、选定资料、版本号 | 新发布目录 |
| 核对文件 | 清单与实际字节 | 完整性通过或明确失败 |
| 建库运行 | 最终位置、配置 | 当前版本的索引和服务 |
| 验证功能 | ready、固定查询 | 可用证据 |
| 恢复旧版 | 保留目录和恢复步骤 | 再次验证的旧服务 |

校验只核文件与清单一致。若清单和文件一起被改，不能靠这份无签名清单证明作者或安全性。

## 常见疑问

**Git 提交、GitHub Release 和这里的发布一样吗？**不是同一动作。提交保存版本库内容；GitHub Release 是发布平台产物；当前 release.py 只创建本地运行目录。

**版本回滚会恢复所有业务数据吗？**当前没有数据库迁移、外部写入或流量切换，只恢复本地脚本、配置和选定资料。真实业务若改了数据，需要另设计备份与兼容策略。

**两个版本能同时用同一端口吗？**通常不能同时绑定同一地址端口。演练时先停止新版本，或用 --port 临时另选测试端口。

**新版本摘要通过能直接宣布可用吗？**还要检查启动、就绪、实际功能和评估。完整性不等于正确性。

**运行 Python 后多了缓存文件怎么办？**严格 verify 会拒绝 .local 以外的额外文件。可用 Python 的 -B 选项避免生成字节码缓存，保持发布目录清晰。

## 小练习与自测

**题目：**只保留版本号，没有保存对应代码与资料，能可靠回滚吗？

**参考答案：**很难。需保留明确内容、环境要求与步骤，并真正验证旧版能启动和查询。

**练习：**只改新实验包文件观察校验失败，原版保留完整。之后实际启动旧版并记录恢复结果，不能仅凭 verify 代替恢复演练。
