# Agent 记忆与上下文

[卡片目录](README.md) · [第四阶段课程](../20-课程笔记/第四阶段-工具调用与Agent课程及实践顺序.md)

## 一句话解释

**上下文是本次请求实际带给模型的信息；记忆是系统保存后、在需要时再次取出的信息。**桌面上摊开的资料像上下文，书架上的笔记像外部存储；在书架上不等于这次已经读过。

## 为什么需要它

用户容易以为“我存过这篇笔记”就等于“模型永久记住”。实际上，每次请求带了什么、工具查到了什么，都由应用组织。

长期保存可以避免重复整理，但也可能保留错误和过期内容。需要知道来源、适用时间和更新方式；否则旧结论会不断进入新回答。记忆管理是数据管理问题，不只是多放一些文本。

## 用 MindVault 走一遍

第一次运行密钥出题任务时，最初只有规则与任务，尚未读取原文。搜索回执进入 messages，读取原文再次进入 messages；程序还把读取证据保存到 evidence。第三轮才拥有完成题目所需的信息。

关掉程序再启动，当前代码重新创建 messages 和 evidence。即使之前保存了 messages.json，也不会自动加载。因此第二次不是“接着上次聊”，而是新会话。

| 内容 | 存在哪里 | 怎么进入模型视野 |
| --- | --- | --- |
| 本次会话状态 | 内存中的 messages 等 | 组装进当前 API 请求 |
| 外部知识 | 选定的 Markdown | 经搜索、读取、回传 |
| 历史运行记录 | 本地 JSON 与 Markdown | 当前无自动加载，需要另做读取设计 |
| 未来长期偏好 | 可设计专门存储 | 当前未实现，需要选择和注入相关信息 |

假设以后保存“我正在学 Agent，喜欢用生活类比”，这属于可更新的学习偏好；一次网络超时日志通常只是临时诊断。不要把所有错误信息和整段旧对话都长期送入每个新请求。

这个例子只是未来设计说明，本库没有自动用户画像、跨会话记忆或历史摘要功能。

## 每一步的输入输出

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 新建会话 | 本次任务 | 初始 messages |
| 搜索与读取 | 当前资料 | 相关工具结果 |
| 累积状态 | 旧消息与新回执 | 下次请求上下文 |
| 检查长度 | 序列化消息与工具说明 | 继续或 context_limit |
| 保存和重启 | 本地运行记录 | 保存供回看；新运行仍从初始状态开始 |

持久化指保存后仍存在；恢复会话指重新读取并重建状态。前者做了，不代表后者已实现。

## 常见疑问

**多放历史就一定更好吗？**不一定。无关信息增加长度和成本，旧状态可能干扰当前任务。优先保留任务、约束、有效证据和必要错误反馈。

**超过上下文预算会自动摘要吗？**当前不会。消息与工具定义合计超过 24000 字符就停止；字符不是 Token。自动摘要需要后续实现，也要检查是否丢失原文出处与限制。

**有 RAG 就有长期记忆吗？**RAG 可以帮助取回保存的内容，但还需要决定保存什么、何时更新、如何删除和何时检索。仅检索知识文档不等于自动管理个人长期记忆。

**压缩后只留答案可以吗？**可能丢掉来源、资料版本和错误状态。未来若做摘要，至少要保留结论的依据与适用范围，不能把未经核对的答案变成可信事实。

## 小练习与自测

**题目：**第二次运行不知道上一轮读过哪篇笔记，是模型“记性差”吗？

**参考答案：**先检查应用是否恢复历史。本库没有恢复逻辑，第二次请求没有上次消息是预期行为。

**练习：**把“学习偏好”“一次失败请求的原文”“已核实的知识卡片”分成长期可保存和临时信息，并写出未来更新或删除方式。分类取决于用途，不是越多越好。

### 动手记录

- [ ] 运行两次，确认第二次没有自动带入第一次的结果。
- [ ] 指出任务中哪些内容适合保存为笔记，哪些只需临时使用。
