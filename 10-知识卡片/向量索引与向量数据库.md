# 向量索引与向量数据库

[第三阶段阅读顺序](../20-课程笔记/第三阶段-RAG课程与实践顺序.md) · [项目 03](../30-项目实践/03-RAG知识库问答/README.md)

## 一句话解释

**索引是为了方便查找而组织的信息；向量索引用向量相似度找候选；向量数据库进一步提供存储、查询和数据管理等能力。**

可以把索引想成书后的检索表，把数据库想成管理整批资料的系统。不同工具提供的能力不同，不能只看名字里有没有“向量”。

## 为什么需要它

每问一次问题，都重新读所有文件、切分并计算全部文档向量，会重复大量工作。预先保存片段和向量，提问时主要计算问题向量，就能复用准备结果。

注意，“索引”有宽窄两种常见用法。本项目说的 JSON 索引，是包含片段和来源的可查询快照；更大系统里说的向量索引，往往还包含专门加速近邻搜索的数据结构。一个 JSON 文件不会因为叫“索引”就自动获得快速近邻算法。

## 用 MindVault 走一遍

假设把若干篇笔记切成 A、B、C 三个片段。本项目语义索引需要维持这样的对应关系：

| 位置 | 片段信息 | 向量信息 |
| --- | --- | --- |
| 0 | A 的 ID、原文和文件位置 | A 的向量 |
| 1 | B 的 ID、原文和文件位置 | B 的向量 |
| 2 | C 的 ID、原文和文件位置 | C 的向量 |

问“API 密钥应该放在哪里，能写进 Git 吗？”时，先产生问题向量，再与 A、B、C 的向量逐个比较。若 A 分数最高，就取回 A 的原文和来源，而不仅返回“一串数值很接近”。

本项目索引里，`manifest` 记录文件路径和摘要，帮助检查资料是否变化；`chunks` 保存片段及来源；语义模式另外保存 `vectors`。这几部分必须对应，只有向量而丢失原文，模型就没有可引用的材料。

## 每一步的输入输出

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 建库 | 资料和切分配置 | 片段与来源 |
| 编码，可选 | 片段和 Embedding 模型 | 文档向量 |
| 保存快照 | 片段、模型信息、文件摘要 | 索引文件 |
| 查询 | 问题及索引 | 候选的 ID、分数 |
| 回查 | 候选 ID | 原文与引用位置 |
| 更新 | 变化后的资料 | 与新资料一致的新索引 |

本项目关键词索引没有文档向量，查询时按字面特征打分。两种路径都能通过 ID 和来源回到笔记。

## 精确遍历与近似搜索怎么理解

精确遍历会把问题向量与每个片段向量都比较一次。假设有 N 个片段、每个 d 维，一次查询大致需要 N×d 量级的数值运算。对小实验，这种做法容易理解和检查。

近似最近邻搜索会利用额外的数据结构减少比较工作，以更快找到相近候选，但可能遗漏部分本应靠前的结果。它优化的是查找速度与召回的取舍，不会判断资料是真是假。本库目前没有实现近似最近邻算法。

## 常见疑问

**五篇笔记要先装数据库吗？** 可以先用现有 JSON 与精确遍历完成实验。遇到规模、持续更新、过滤或并发需求，再明确评估需要什么能力。

**换数据库后答案就会更准吗？** 数据库不会自动修正错误笔记、糟糕切分或错误生成。先定位问题再选工具。

**数据库和原文哪个重要？** 本项目索引可根据 Markdown、配置和模型重新生成；原文、实验配置及来源要保留。未来如果有只存于数据库的人工标签，也应另行备份。

**为什么不能拿别人的索引直接混用？** 模型、维度、切分、资料版本或文件路径都可能不同。当前索引还带本机资料目录信息，需要核对后才能使用。

## 小练习与自测

不运行模型，画三列：“片段 ID、原文位置、向量位置”。解释删除 B 后为什么不能只删正文、把原有向量列表原样留下。

参考答案：数据之间的对应关系会错位或留下陈旧候选，检索分数可能指向错误原文。删除和更新必须保持关联一致。

## 本库实现与实践入口

当前实现保存 JSON，语义模式逐个计算归一化向量的点积，没有部署向量数据库。索引属于本地派生数据，默认放在被 Git 忽略的 `.local/`。

先在[实践一](../30-项目实践/03-RAG知识库问答/实践一-加载切分与关键词检索.md)打开关键词索引；语义结构在[实践三](../30-项目实践/03-RAG知识库问答/实践三-语义检索与索引更新.md)中选修。重建练习使用新文件名，避免覆盖已有结果。
