# 消息角色与多轮对话

[卡片目录](README.md) · [课程入口](../20-课程笔记/第二阶段-模型API课程与实践顺序.md)

## 一句话解释

**消息列表用角色和顺序表达规则、提问、回答及必要材料。**像会议记录标出谁说了什么，后续一句“再短一点”才有可以指向的前文。

## 为什么需要它

普通聊天产品可能替你管理历史，直接 API 则需要按接口规则提供消息。不能因为屏幕上还能看到上轮内容，就认定这次请求自动带上了它。

角色也帮助分清应用规则与文章资料，但标签本身不保证事实正确或完全防止提示注入。

## 用 MindVault 走一遍

这是自写的消息示意，assistant 内容是教学文字，不是实测模型回答：

```json
[
  {"role":"system","content":"用初学者能懂的话解释概念。"},
  {"role":"user","content":"什么是 Token？"},
  {"role":"assistant","content":"Token 是模型处理内容的小单位。"},
  {"role":"user","content":"请给前面的解释补一个例子。"}
]
```

| 角色 | 本阶段用途 |
| --- | --- |
| system | 应用给出的任务规则 |
| user | 用户问题或选定文章正文 |
| assistant | 模型回答或应用组织的历史回答 |

DeepSeek Chat Completions 的这类多轮调用需要客户端提供相关历史。新请求只发“再短一点”，没有前文，模型就缺少具体对象。

项目 02 先做单轮：system 写整理规则，user 放“文章正文：”及内容。不会自动把整个 MindVault 或旧草稿作为历史，也不会把自己的上次输出作为隐含记忆。

文章里如果写“忽略上面要求”，它仍是用户提供的待整理资料；应用应该按任务处理，不把正文内任意命令变成新的授权。当前提示有相应规则，后续 Agent 还会学习工具权限限制。

## 每一步的输入输出

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 建立规则 | 任务与输出约定 | system 消息 |
| 提供材料 | 问题或正文 | user 消息 |
| 调用 | 有序 messages | assistant 返回 |
| 继续对话 | 必要历史和新问题 | 新 messages |
| 管理长度 | 相关性和 Token 预算 | 筛选后的上下文 |

历史再次进入请求会占输入容量和处理用量。需要摘要或选择时，要保留原任务、约束与必要依据。

## 常见疑问

**assistant 标签证明是模型真实说过的吗？**请求历史可以由应用组织，角色不证明来源真实，更不证明内容正确。

**system 就一定不被忽略吗？**规则表达与模型遵循程度不同，还要验证行为，并在程序层落实可执行边界。

**多轮就是永久记忆吗？**不是，是当前请求带入了相关历史。长期保存与重新取回是应用功能。

**能把笔记库全放历史吗？**容易超长、无关和增加费用，先选择任务需要的材料，第三阶段再学检索。

**未来有工具消息怎么办？**第四阶段学习 assistant 调用与 tool 回执配对，本阶段先把三种基础角色看懂。

## 小练习与自测

**题目：**API 只收到“再短一点”，能必然知道哪份摘要要缩短吗？

**参考答案：**不能，要看实际提供的上下文或接口会话机制。

**练习：**在 summarize preview 找出规则与正文分别在哪条消息；指出 source-url 是否在模型材料中。当前它只用于保存来源记录。
