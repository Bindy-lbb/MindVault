# 消息角色与多轮对话

[知识卡片目录](README.md) · [第二阶段课程](../20-课程笔记/第二阶段-模型API课程与实践顺序.md)

## 一句话解释

**消息列表按角色和顺序提供任务与对话材料。**本阶段先使用 `system`、`user`、`assistant` 三种角色理解简单对话；具体接口还可能支持其他角色。[接口参考](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)

## 用生活里的事理解

像给会议记录标注“规则”“提问”“回答”。保留谁说了什么、先后顺序，才能理解后续“再短一点”指的是什么。

## 一个具体例子

```json
[
  {"role": "system", "content": "用初学者能理解的话解释概念。"},
  {"role": "user", "content": "什么是 Token？"},
  {"role": "assistant", "content": "Token 是模型处理内容的小单位。"},
  {"role": "user", "content": "请补充一个例子。"}
]
```

这是自拟的消息拼接示意，其中的回答为教学文字，不是一次已执行的模型结果。

## 为什么要自己提供历史

DeepSeek 的 Chat Completions 接口按无状态方式使用；多轮时需要在请求中提供相关历史。不同产品可能另有会话管理方式，不能只凭聊天界面的体验推断所有 API 都会自动记住。[依据：官方多轮对话指南](https://api-docs.deepseek.com/zh-cn/guides/multi_round_chat/)

## 放到 MindVault 中有什么用

整理文章时，用说明消息明确任务，用用户消息提供正文。文章中的文字作为资料处理，不能因其中出现命令就当成应用的任务要求。

## 容易误解的地方

- 历史消息进入本次请求后，也会占用上下文。
- `assistant` 消息在请求中可以是应用组织的历史，不能仅凭角色标签认定其事实可靠。
- 本项目先做单轮任务，避免一开始就把所有笔记作为历史发送。
