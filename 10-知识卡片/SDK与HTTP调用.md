# SDK 与 HTTP 调用

[卡片目录](README.md) · [课程入口](../20-课程笔记/第二阶段-模型API课程与实践顺序.md)

## 一句话解释

**直接 HTTP 需要自己组织请求和解析响应；SDK 是把常见调用封装成函数或对象的软件工具包。**像自己逐项填表，或使用填表助手，最终仍要遵守服务接口规则。

## 为什么需要它

教程中的几行 SDK 代码可能隐藏了请求构造、错误转换和重试等步骤。先看懂底层消息，就能知道换工具时哪些行为相同、哪些需要重新核对。

本库前两阶段先用标准库，减少安装步骤，方便直接观察输入、输出和失败。

## 用 MindVault 走一遍

同一个文章整理任务，无论写 HTTP 还是用 SDK，都要提供模型、消息、认证，最后检查生成结果。

| 环节 | 本库直接 HTTP | SDK 常见封装，依实际库而定 |
| --- | --- | --- |
| 配置 | 固定 endpoint 与头 | 客户端对象的地址与凭据 |
| 请求 | json.dumps、Request、open | 某个生成方法 |
| 响应 | JSON 字典 | 字典或响应对象 |
| 失败 | HTTPError 等转提示 | SDK 自身异常类型 |
| 结果核对 | 本地校验与人工复核 | 同样仍需做 |

这里描述职责，不给出某家 SDK 的可执行签名，避免把不同版本的方法混用。选择 SDK 时要核对包名、版本、接口兼容性和默认行为，尤其超时、重试与日志。

安装 SDK 不会获得服务余额或 Key。服务声称接口兼容，也不代表所有字段、工具调用和返回类型都完全一致，要以目标服务文档和实际结果为准。

Datawhale 课程中若使用 SDK，可以把它拆成“构造输入 → 提交 → 取回答 → 保存”对应本项目；先理解结构，再迁移写法。

## 每一步的输入输出

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 明确任务 | 模型接口与需求 | 所需能力 |
| 选择方式 | 直接 HTTP 或适配 SDK | 客户端实现 |
| 核对版本 | 文档、包版本、默认配置 | 可解释的调用设置 |
| 最小调用 | 短任务和有效凭据 | 返回或错误 |
| 保留应用检查 | 字段、事实和来源 | 可接受草稿 |

库负责便利封装，应用仍负责业务规则和数据边界。

## 常见疑问

**SDK 一定会自动重试吗？**不同库与版本不同，应查默认值。不能把本库“不自动重试”的结论原样套到新 SDK。

**改为 SDK 就不用懂 JSON 了吗？**仍要理解字段与类型，否则难判断请求和返回哪里不符。

**SDK 方法名等于 HTTP 字段名吗？**不一定，可能有重命名、对象包装或额外选项。

**标准库调用更正确吗？**不是质量高低比较。教学先展开机制，之后按维护、支持和需求选择。

**SDK 能避免幻觉吗？**它方便调用，不替代事实与依据验证。

## 小练习与自测

**题目：**换了 SDK 后重复请求次数变多，先查什么？

**参考答案：**查 SDK 默认重试、超时和应用自身循环，不只怀疑模型生成。

**练习：**在教程里找一段 SDK 示例，只标出配置、输入和返回位置，再对照本库 call_api，不急于安装。
